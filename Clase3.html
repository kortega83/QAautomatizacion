Apertura: el archivo que nadie sabe cuál es

Objetivo: que sientan el problema antes de ver la herramienta.

TeoríaEl gancho

¿Te suena una lista como esta?

test_script.py
test_script_v2.py
test_script_FINAL.py
test_script_FINAL_v2.py
test_script_OK_REAL.py

Pensá: ¿cuál de estos corrió en el último release? ¿Quién lo cambió y por qué? No hay forma de saberlo. Esa es la pregunta que el historial de Git responde.

PrácticaDiagnóstico rápido

Respondé en el chat o con una reacción: ¿quién tiene cuenta? ¿quién usó Git alguna vez? ¿quién trabajó en equipo sobre el mismo archivo?

¿Por qué GitHub? Control de versiones y por qué le importa a QA

Objetivo: distinguir Git de GitHub y entender por qué una suite de automatización es código como cualquier otro.

Por qué importa en QA Automation

  • Tu suite de tests es código. Se rompe, se refactoriza y se revisa como el código de la aplicación.
  • Casi toda oferta de QA Automation pide Git. Los pipelines de CI arrancan desde un repositorio.
  • El historial es evidencia: cuándo se agregó un caso, cuándo dejó de pasar, quién lo tocó.

Según el módulo de Microsoft Learn, GitHub es una plataforma colaborativa que usa Git para versionar, y es un lugar muy usado para compartir y contribuir a software de código abierto.

PrácticaTu perfil (3 minutos)

  1. Entrá a github.com/<tu-usuario> y confirmá que se ve tu nombre de usuario.

  2. Un repositorio público con el mismo nombre que tu usuario muestra su README en tu perfil. Es una tarjeta de presentación para reclutadores. Lo vamos a dejar como extra de la tarea.

Autoevaluación

¿Si se rompe tu laptop esta noche, qué pasa con tu suite de tests? ¿Y si un compañero pisa tu script?

Respuesta: con GitHub el código y su historial están en otro lugar; las ramas evitan pisarse.

PrácticaMisiones en un repositorio público (10 minutos)

Cada alumno elige uno de estos repositorios de automatización y resuelve las misiones: microsoft/playwright, SeleniumHQ/selenium o pytest-dev/pytest. Cuando termines una misión, escribí en el chat qué encontraste.

  1. Explicá en una frase qué hace el proyecto.

  2. ¿Quién lo hizo y qué dice el mensaje? ¿Se entiende sin abrir el código?

  3. ¿Cuál es la rama por defecto? ¿Cuántas ramas hay?

  4. En Issues buscá uno con una etiqueta tipo bug. ¿Trae pasos para reproducirlo, resultado actual y esperado?

  5. ¿Quién lo revisó? ¿Qué verificaciones automáticas aparecen al final?

  6. Buscá la carpeta .github/workflows. ¿Qué archivos hay? No hace falta entenderlos, solo ubicarlos.

Demo en vivo

Flujo de trabajo: crear, commitear, mirar el historial, repetir

Objetivo: que cada alumno tenga su primer repositorio con al menos tres commits. El ciclo se hace dos veces porque la segunda es la que hace clic.

TeoríaQué es un commit y cómo se escribe uno (5 minutos)

Un commit es una foto del proyecto con un mensaje que explica qué cambió y por qué. En el editor web, el botón Commit changes hace de una vez lo que en la terminal son tres pasos (add, commit y push). Esa equivalencia sirve de puente para la sesión de instalación de Git.

MensajePor qué
cambiosNo dice qué ni por qué
arreglé cosas v2Reproduce el problema de los archivos _FINAL
Agrega checklist de casos de prueba para loginDice qué se agregó y dónde
Agrega casos negativos: contraseña vacía y usuario bloqueadoAlguien que lea el historial entiende la intención

PrácticaCiclo 1: crear y commitear (10 minutos)

  1. Botón New en la página principal. Nombre: qa-automation-practica. Público. Marcá Add a README file. Opcional: plantilla .gitignore de Python.

  2. Add file → Create new file. Nombre: tests/checklist-login.md (escribir la barra crea la carpeta). Pegá el contenido de abajo.

    ## Checklist de login

- [ ] Login con usuario y contraseña válidos
- [ ] Login con contraseña incorrecta muestra error
- [ ] Login con usuario inexistente muestra error

  3. Commit changes. Mensaje sugerido: Agrega checklist de casos de prueba para login. Dejá la opción de commitear directo a main.

  4. En la página del repositorio, tocá el contador de commits. Deberían ver dos: el inicial y el tuyo.

PrácticaCiclo 2: editar y repetir (10 minutos)

  1. Abrí el archivo, ícono del lápiz. Agregá dos casos negativos: - [ ] Login con contraseña vacía muestra error y - [ ] Login con usuario bloqueado muestra error. Commit: Agrega casos negativos: contraseña vacía y usuario bloqueado.

  2. Abrí ese commit desde el historial. Las líneas en verde se agregaron y las rojas se borraron. Esto es lo que ve un revisor.

  3. Creá tests/test_login.py con este esqueleto, que falla a propósito. Lo vamos a usar en el bloque 4. Commit: Agrega esqueleto de test de login con contraseña vacía.

    def test_login_con_contrasena_vacia_muestra_error():
    # TODO: implementar con Selenium o Playwright
    assert False, "pendiente de implementar"

PrácticaMini reto: encontrar al culpable (5 minutos)

  1. Tu pareja es la persona que te asigna el facilitador en el chat. Como están a distancia, pásense el link de su repositorio por mensaje directo. Cada uno edita una línea de su propio checklist con un cambio absurdo, lo commitea y avisa. Tu pareja abre tu archivo, toca Blame y encuentra qué commit cambió esa línea y cuándo. Es el mismo razonamiento que se usa para rastrear una regresión.

Autoevaluación

¿Qué información da el historial que un archivo llamado _FINAL_v2 no puede dar?

Respuesta: quién, cuándo, qué cambió exactamente (diff) y por qué (mensaje).

Teoría y práctica

Colaboración y conexión con QA: ramas, issues y pull requests

Objetivo: recorrer un ciclo completo de GitHub flow: reportar un bug, arreglarlo en una rama, pedir revisión y unir el cambio.

TeoríaGitHub flow en seis pasos (5 minutos)

La regla de oro: lo que está en main siempre funciona. Todo cambio se prueba en una rama aparte y se une solo después de una revisión.

Esto conecta con el módulo de Microsoft Learn, que trata ramas, commits y pull requests como los componentes del flujo de GitHub. El pull request es el hábito clave de QA integrado en la plataforma: antes de que el código entre, alguien lo revisa.

Si te da curiosidad otro modelo de ramas, el famoso git-flow está explicado en la sección Git flow vs GitHub flow.

PrácticaUn ciclo completo (15 minutos)

  1. Pestaña Issues → New issue. Título: Bug: el login acepta contraseña vacía. Cuerpo:

    **Pasos para reproducir**
1. Abrir la pantalla de login
2. Ingresar un usuario válido
3. Dejar la contraseña vacía y enviar

**Resultado actual**
El sistema permite el ingreso.

**Resultado esperado**
Mensaje de error y sin acceso.

**Entorno**
Navegador y versión:

    Anotá el número que recibe el issue (probablemente #1).

  2. En la página del repositorio, desplegable de ramas (dice main), escribí fix/login-contrasena-vacia y elegí Create branch. Nombres descriptivos con prefijo (fix/, test/, docs/) hacen legible la lista de ramas.

  3. Confirmá que estás parado en la rama nueva. Editá tests/test_login.py y reemplazá el contenido por el siguiente. Commit: Implementa verificación de contraseña vacía en test de login.

    def login(usuario, contrasena):
    # Simulación mínima del sistema bajo prueba
    return bool(usuario) and bool(contrasena)


def test_login_con_contrasena_vacia_muestra_error():
    assert login("ana", "") is False

  4. Compare & pull request. En la descripción escribí Closes #1 (o el número de tu issue). Eso enlaza ambos y cierra el issue solo cuando se una el cambio. Copiá el link del pull request: lo vas a usar en el paso siguiente.

  5. No hace falta estar en la misma sala ni compartir pantalla: la revisión se hace con comentarios en GitHub. Pasale a tu pareja el link de tu pull request por mensaje directo y pedile el suyo. Abrí el pull request de tu pareja, andá a Files changed, dejá un comentario en una línea y envialo con Review changes → Comment. Como los repositorios son públicos, no hace falta darle permisos a nadie.

    Si no tenés pareja, o no te responde en unos minutos, revisá el pull request de práctica que el facilitador pega en el chat.

  6. Leé el comentario de tu pareja y respondelo. Si pasaron unos minutos sin revisión, seguí igual. Después, Merge pull request → Confirm. Verificá que el issue se cerró solo y tocá Delete branch.

DemoExtra: tests corriendo solos con GitHub Actions

Es la parte que más conecta con QA Automation y la vamos a explorar con más detalle más adelante. Si querés adelantarte, creá .github/workflows/tests.yml en main:

name: tests
on: [push, pull_request]

jobs:
  pytest:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest
      - run: pytest

Qué mirar: en main el test de ejemplo falla si todavía tiene el assert False, y eso aparece como una cruz roja. Con la rama arreglada, el pull request muestra una verificación verde. Es la idea de "ningún cambio entra sin pasar los tests". Las versiones de las acciones cambian con el tiempo; consultá su documentación para usar las vigentes.

Autoevaluación

¿Por qué no commitear directo a main cuando el equipo es de más de una persona?

Respuesta: porque main debe estar siempre estable; la rama y el pull request permiten probar y revisar antes de unir.

TeoríaRepaso en tres preguntas (3 minutos)
1. ¿Cuál es la diferencia entre Git y GitHub?

Git registra los cambios; GitHub es la plataforma para guardarlos y compartirlos.

2. ¿Qué hace que un mensaje de commit sea bueno?

Dice qué cambió y por qué, sin necesidad de abrir el código.

3. ¿Para qué sirve un pull request?

Para pedir una revisión antes de unir cambios a main.

Git flow (nvie) frente a GitHub flow

Material extra para quien quiera ir más allá de la charla.

Qué propone el artículo de nvie

En 2010, Vincent Driessen publicó A successful Git branching model: un modelo para software que se entrega por versiones. Define cinco tipos de ramas, dos permanentes y tres temporales.

RamaVivePara qué
main (en el artículo: master)SiempreSolo código publicado; cada commit es una versión.
developSiempreIntegración de lo que viene para la próxima versión.
feature/*TemporalUna funcionalidad. Sale de develop y vuelve a develop.
release/*TemporalPreparar una versión: correcciones finales, número de versión. Se une a main y a develop.
hotfix/*TemporalArreglo urgente sobre producción. Sale de main y se une a main y a develop.
Por qué empezamos por GitHub flow

El propio autor agregó una nota al artículo diciendo que, si el equipo hace entrega continua, conviene un flujo mucho más simple como GitHub flow en vez de forzar git-flow. Para dar los primeros pasos, cinco tipos de ramas con reglas de unión distintas son más de lo necesario.

Comparación

GitHub flowGit flow
Ramas permanentesUna (main)Dos (main y develop)
Ideal paraEntrega continua, equipos chicos, suites de testsSoftware con versiones numeradas y varias versiones en producción
Complejidad para aprenderBaja: 6 pasosMedia o alta: 5 tipos de ramas
Dónde lo vas a verProyectos de código abierto y startupsEmpresas con ciclos de release largos

Dónde aparece QA en git-flow

  • La rama release/* suele coincidir con la ventana de regresión: se congela lo nuevo y solo entran correcciones.
  • Un hotfix/* pide una verificación rápida y focalizada, porque va directo a producción.
  • Los pull requests hacia develop son el momento natural para correr la suite automatizada.
